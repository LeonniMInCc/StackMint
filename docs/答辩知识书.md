# 栈点项目答辩知识书

这份说明对应本地源码。先运行系统，再顺着一次购买过程阅读，比背概念更容易。工程含 AI 辅助生成内容，不能把本文当成独立手写开发经历的证明。

## 1. 系统到底做什么

这是一个数字商品商店，不是炒币平台。卖的是API调用次数、兑换码和简单数字服务。用户注册后，在演示环境获得100元虚拟余额，可以购买商品，立即获得自己的凭证，然后在页面或接口中使用。

兑换码是本系统的演示授权，不会激活真实商业软件。代码检查服务只有固定规则，例如发现var或eval时提示，不是AI编程助手。API中的关键词只是分词后的前几个不同词，不是复杂语义分析。

## 2. 五分钟演示顺序

1. 打开首页：展示分类、搜索、价格和库存，解释页面参考社区列表的信息组织方式。
2. 注册新账户：昵称、邮箱、至少10位密码。演示余额100元。
3. 买19元API：余额变为81元，订单出现，得到独立API Key和1000次额度。
4. 试用：输入一段文本，执行一次，剩余次数999；使用记录中新增一条。
5. 买兑换码：查看凭证，兑换一次，再次兑换按钮不可用；后端也会拒绝重复兑换。
6. 退出并用管理员登录：展示上架、下架、补货和审计。

演示过程中不要在投屏上展示将来真实部署环境的密码或API Key。本地示例凭证只用于演示。

## 3. 三层结构怎么理解

React像柜台，负责把商品、余额、按钮显示出来。Express像收银员，判断身份、价格、余额和库存是否符合规则。SQLite像账本，持久记录用户、订单和使用记录。

浏览器不能直接改账本。点击按钮后，通过fetch发HTTP请求，后端处理后返回JSON。React拿到JSON更新状态，页面重新显示。刷新网页不是把数据清空，因为订单在SQLite文件中，而不是只存在React变量里。

启动时，server/db.js先连接数据库并建表，再初始化不存在的商品和演示账户。server/index.js加载它，注册中间件和接口，监听3000端口。前端由Vite构建到dist，然后由同一个Express服务提供，避免本地前后端跨域配置。

## 4. 从点击购买到交付，逐步跟代码

在src/main.jsx找到type:'buy'：点击商品时创建弹窗和requestKey。requestKey是这一次购买尝试的唯一编号，失败重试仍用同一个值。

确认后调用send('/orders', {productId, requestKey})。send把对象转为JSON，api用fetch发送到/api/orders。请求携带浏览器自动管理的Cookie。

server/index.js中的auth读取Cookie，先算摘要，再查sessions表，判断会话是否过期，然后从users读取实际身份和角色。后续使用req.user.id，绝不相信客户端自称的用户ID。

购买路由先检查参数，再进入transaction：
- 查询这个用户是否已用过requestKey；有则返回旧订单，避免双击扣两次钱。
- 从数据库查询商品和价格，不能相信前端发送的金额。
- 如果是兑换码，找一个used=0的库存项。没有库存则失败。
- 扣余额，SQL要求balance>=price；失败则余额不足。
- 分配兑换码或生成新凭证；写订单快照和审计。
- COMMIT提交。任一步失败则ROLLBACK，之前的扣款也撤回。

最后orderView解密本人凭证，返回JSON。React调用refresh重新取余额、订单和使用记录，切到“我的资产”。前端禁用提交按钮只是改善体验，真正防重复靠后端唯一约束和事务。

## 5. 数据库表之间的关系

| 表 | 负责什么 | 主要关系 |
| --- | --- | --- |
| users | 邮箱、密码摘要、角色、余额 | 一个用户有多笔订单 |
| sessions | 登录会话摘要和过期时间 | 指向users |
| products | 商品描述、分类、价格和额度 | 一个商品对应很多订单 |
| inventory | 加密的兑换码和是否已售出 | 指向products |
| orders | 买家、商品快照、凭证、剩余额度 | 指向users和products |
| usage | 一次使用或兑换的记录 | 指向orders和users |
| audit | 管理或交易操作记录 | 保存操作者和操作描述 |

余额、价格用整数“分”，避免浮点计算中0.1+0.2的精度问题。19元在数据库是1900。

库存和额度不同：库存是“还剩多少份可卖的兑换码”，额度是“某笔已购买订单还能调用几次”。商品下架只禁止新增购买，不删除已购订单。订单保留当时的名称和金额，不能随着商品修改而改历史账单。

## 6. 使用接口怎么扣次数

网页试用走/api/orders/:id/use，先核对订单属于当前用户。外部调用走/api/v1/analyze，使用Authorization: Bearer TOKEN查询订单。两条路线最后都调用consume。

consume在事务里执行remaining=remaining-1，条件是remaining>0。没有更新到行说明次数已用完；成功后生成结果、插入usage记录。这样两个并发调用不能把次数扣到负数。

在PowerShell里用自己的测试凭证：

```powershell
$headers = @{ Authorization = 'Bearer 这里填自己的APIKey' }
$body = @{ text = '你好，栈点' } | ConvertTo-Json
Invoke-RestMethod -Uri 'http://localhost:3000/api/v1/analyze' -Method Post -Headers $headers -ContentType 'application/json' -Body $body
```

当前使用接口没有请求幂等编号，网络重试可能再扣一次；只有购买接口实现了幂等。答辩时不要把两者混淆。

## 7. 安全问题，用普通话说明

密码哈希：像只留指纹，登录时再算一次对比，不能拿指纹还原密码。scrypt加随机盐，避免相同密码得到相同存储值。

凭证加密：像把商品码放进有钥匙的盒子。用户以后还要查看原码，因此需要可逆加密。AES-GCM还会检查密文有没有被篡改。vault.key就是钥匙，丢了不能恢复凭证。

会话：登录时发随机票据，浏览器Cookie保存，数据库只存票据摘要。HttpOnly让普通网页脚本读不到票据，SameSite=Strict减少跨站携带。退出时删除数据库会话。

越权：把别人的订单编号填到地址里，也必须查user_id是否匹配。管理员权限则每次请求从数据库角色判断，不能靠前端隐藏按钮。

SQL注入：SQL用?占位符绑定参数，不把输入拼成SQL命令。XSS：React把文本转义，不用dangerouslySetInnerHTML渲染输入。CSRF：严格Cookie和写请求Origin检查配合使用；命令行无Origin请求仍允许，但必须有认证。

限流：同一IP在一分钟内请求太多就拒绝。当前存在内存里，重启清零，适合单实例课程演示，不是分布式防攻击系统。

边界：密钥与数据库放在同一台机器，不能防整台服务器被攻破；日志也不是不可篡改。上线前必须处理演示账号、HTTPS、备份和进程守护。不能宣称“绝对安全”。

## 8. React里最重要的几个状态

user是当前用户；page决定显示哪个页面；products/orders/usage保存服务器返回数据；category和query决定前端筛选；modal决定弹窗；busy禁用重复提交；error和notice显示错误或成功反馈。

useEffect在首次加载时获取配置和数据，也用于通知定时消失和Escape关闭弹窗。setState触发重新渲染，但不会直接修改数据库。需要持久保存的变化必须经过后端接口。

样式分两层：style.css是表单、弹窗、订单等基础样式；community.css是社区集市主题，后加载覆盖颜色与列表布局。PixelCat是本地SVG组件，使用小格子绘制，不会发网络请求。

## 9. 现场改代码练习

### 把注册赠送余额改成50元
找到server/index.js注册路由里的demo?10000:0，改成demo?5000:0。重启服务，注册新账户验证。旧账户不会自动改变。db.js中的初始演示用户另有默认余额，不能认为改一处就改了所有旧数据。

### 会话改成2小时
找createSession，数据库expires与cookie maxAge中的86400000都改为7200000。只改Cookie或数据库一边会导致行为不一致。现有会话不自动迁移，重新登录再测。

### 新增商品字段
例如给商品增加“适用场景”：需要数据库ALTER TABLE迁移、管理员输入和后端校验、INSERT字段、前端展示。CREATE TABLE IF NOT EXISTS不会给已有表自动加列。先备份再迁移。

### 新分类
至少改前端categories和icons映射、后台校验白名单、订单交付规则。不能只加一个下拉选项，因为新分类到底交付什么需要业务定义。

### 改每次调用扣两次
consume中的扣减改为remaining-2，条件也要改remaining>=2；同步页面文案、额度测试。只改减法不改条件会出现负数。

### 改主题颜色
先改community.css中主要绿色按钮、导航、分类线和像素配色；npm run build后刷新浏览器。不是直接改dist压缩文件，dist下次构建会被覆盖。

## 10. 常见答辩问答

为什么选择SQLite？部署简单，单文件便于演示，小型单实例业务够用。它不等于无限并发，规模扩大后可以迁移到服务型数据库。

事务和幂等区别？事务防止一次购买只做了一半；幂等防止同一购买被重复执行。两者解决不同问题。

为什么不能只看前端余额？用户可以改浏览器代码。后端必须自己查余额、价格和库存。

前端刷新后为何还在登录？Cookie还在，会话未过期，/api/me能重新识别用户。

停机再启动是否丢订单？正常情况下不会，SQLite文件持久化。丢密钥或误删data会造成问题，需要备份。

创新在哪？不是算法发明，而是统一三类数字交付、网页试用与API共用额度账本、购买幂等和可追溯记录的组合设计。不要夸大为行业首创。

原创怎么解释？如实说明实际参与和辅助工具使用。代码含AI生成内容，不符合课程明确禁止AIGC的条款，不能谎称全部独立手写。

## 11. 出问题先看哪里

页面打不开：确认npm start仍在运行、端口没被其他程序占用。node:sqlite找不到：核对Node>=24。提示先build：运行npm run build。401重新登录，403检查权限/Origin，409看余额库存额度，429等限流窗口过去。

密码、完整Cookie、API Key和vault.key不要复制到公共问题截图。运行npm test用独立临时库，不修改当前演示账户。
